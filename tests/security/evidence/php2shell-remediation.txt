php2shell-remediation.txt - measured evidence for the PHP2SHELL runtime fix

Scope: the remediation of doc/PHP2SHELL_AUDIT sections 6(a)-6(f) on branch
security/mitigation-2026-09, measured 2026-10-24 on this host. Every row below
is a command's output, pasted as produced. Rows that were NOT measured say so
in section 5; nothing here is inferred from another row.

Vulnerability: PHP2Shell, CVE-2026-109618 (cleanup after an allocation failure
during request parsing) and CVE-2026-109619 (stale request-owned state reused by
a later request on the same worker). Unauthenticated RCE, CVSS v4.0 9.2. Fixed
in PHP 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12. No application code can mitigate
either one: the request is parsed before any entrypoint runs.

Artifacts:
  docker/Dockerfile            new; FROM php:8.3.36-fpm pinned by digest
  docker/docker-compose.yml    builds that image; ini drop-in mount corrected
  docker/php-custom.ini        mitigation lines + corrected unit/syntax bugs
  docker/nginx.conf            client_max_body_size 10000M -> 64M
  doc/freemed.apache.conf      LimitRequestBody 67108864
  debian/control               php5 -> php8.3 (module, cgi, gd, curl, cli, dev)
  scripts/php-runtime-check.sh new gate; wired into `make security-check`

  the repository tree. The probe echoes PHP_VERSION, the SAPI and the ini values
  the request actually ran under.

  GET /freemed/php2shell-probe.php      (FPM SAPI, not CLI)

    {"php_version":"8.3.36","sapi":"fpm-fcgi","session_upload_progress":"",
     "fatal_error_backtraces":false,"register_argc_argv":"","post_max_size":"64M",
     "memory_limit":"2048M","max_file_uploads":"128","mysqli":true,"files":[]}

    Reading of the empty/false values: ini_get() returns "" for an Off boolean
    (session.upload_progress.enabled, register_argc_argv), and
    fatal_error_backtraces does not exist before PHP 8.5, so it reads false on
    8.3 - the directive is shipped unconditionally and ignored here, which is
    what docker/php-custom.ini documents.

  Multipart upload through the same stack - the parser still works after the
  mitigation, and $_FILES is populated:

    curl -F "file=@/tmp/up1m.bin" -F note=hello .../php2shell-probe.php
    {"php_version":"8.3.36",...,"files":{"file":{"name":"up1m.bin","size":1048576,"error":0}}}

  70 MiB body - the new edge cap refuses before PHP parses it:

    dd if=/dev/zero of=/tmp/up70m.bin bs=1M count=70
    curl -F "file=@/tmp/up70m.bin" .../php2shell-probe.php   ->  status=413

  Existing deployment-hardening rules, unchanged by this work:

    /freemed/lib/API.php                              -> 403
    /freemed/help.php/../scripts/security-...sh       -> 403   (curl --path-as-is)

  The application executes on the new interpreter, with a DB and without

    GET /freemed/index.php
      status=302  redirect=/freemed/ui/gwt/www/FreemedInterface.html

5. NOT MEASURED

  * No exploit payload was built, sent, or replayed. Every "fixed" claim here
    is version + configuration + live-behaviour evidence, not a demonstrated
    pre/post exploitation pair. A PoC A/B against this stack is a separate,
    separately-authorised exercise.
  * No production host was inspected. A distro PHP with a backported fix can
    still report 8.3.x below 8.3.36; for those installs the distro advisory is
    authoritative, and the gate's floor can be relaxed deliberately by passing
    a MIN_VERSION argument (record the override and its reason in the
    deployment notes; do not relax it silently).
  * tests/security/module_smoke.php was NOT run: the probe database has an
    empty `modules` registry, so every relayed method would return the vacuous
    "no rows" negative the harness notes describe. The hermetic suites and the
    live entrypoint rows above are what carry the weight instead.
  * The Apache/mod_php layout was not re-measured: no php5 or php8.3 mod_php
    host exists here. doc/freemed.apache.conf's LimitRequestBody is a
    configuration change whose effect was verified on the nginx side only
    (the 413 row); Apache's own enforcement of the same directive is documented
    behaviour, not something this host measured.
  * xdebug's removal from the runtime image (docker/Dockerfile) is a hardening
    choice, not a PHP2SHELL control; nothing measured its performance effect.
