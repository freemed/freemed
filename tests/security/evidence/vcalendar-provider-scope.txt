3. The ACL contract, verified rather than assumed
   3.1 $GLOBALS['acl'] is NOT built for this endpoint: lib/freemed.php includes lib/acl.php
       inside its session block, which a SESSION_DISABLE request skips. The first version of the
       fix called freemed::acl('schedule', 'view') as the brief specifies and it fataled:
         Call to a member function acl_check() on null in lib/API.php:71  (vcalendar.php:180)
       The fix now loads the object on demand at request scope and denies when it is unusable.
   3.2 the gate itself, evaluated on the harness (gacl object constructed, DB consulted):

sapi=apache2handler
SKIP_SQL_INIT defined=no
isset($GLOBALS['acl']) after lib/freemed.php = no
after loading lib/acl.php on demand: gacl object built
acl_check('schedule','view','user',1) = false
acl_check('schedule','view','user',2) = false
acl_check('schedule','view','user',3) = false

       freemed::acl('schedule','view') returns false for a non-admin account, which is the
       fail-closed direction the 403 rows above depend on. It is only ever true here through the
       user_number == 1 short circuit (the "ACL| schedule/view// forced for admin user" syslog
       line in the POST-FIX rows) — see the caveat in section 4.
4. What this evidence does NOT show
   * No ACO row 'schedule'/'view' exists in this schema (SELECT COUNT(*) FROM acl_aco WHERE
     section_value='schedule' AND value='view' -> 0), and the only ARO row is user 1. So the
     "a scheduler may read another provider's calendar" branch is not positively exercised here:
     a site that wants it must create the ACO/ARO rows. The gate fails closed without them.
   * During this work the vendored phpGACL cache failed with
       flock(): Argument #1 ($stream) must be of type resource, false given
     because the container had a root-owned /tmp/default cache directory (drwxr-x--x root:root)
     that www-data could not write. That is a harness artifact of the throwaway stack, not a
     product defect: chowning that directory to www-data made acl_check() work (section 3.2) and
     the endpoint's error path already treats such a failure as "deny", never as "allow".
