# Seed fingerprint — the database state `module-smoke-before.json` / `module-smoke-after.json` were recorded against

Task 2.6e, fix round 1. Companion to `seed-verify.sql` (the deterministic reduced
seed) and to `sweep-notes.md` section 9 (the drift procedure).

## Why this exists

The two smoke artifacts are only comparable to each other if they were produced
against the same reference database. The harness **does** observe row counts:
`PaymentModule` reports

```
"PaymentModule": "SKIP: GetList() returned 1 rows, none with an id"
```

for the single seeded `payrec` row, so a re-seed that yields 0 rows (a cascade
delete) or 2 rows (the `procrec` AFTER INSERT trigger writes a `payrec` row of its
own) moves that entry and manufactures a delta against the committed baseline.
Recording the counts and ids turns "the database was in the right state" from
prose into a check.

## The recorded state (measured, `freemed-verify-db`, MariaDB 10.11.19, schema `freemed`)

Canonical fingerprint query — copy it verbatim, the order is the recorded one:

```sql
SELECT 'entemplate' AS tbl, COUNT(*) AS n, GROUP_CONCAT(id ORDER BY id) AS ids FROM entemplate
UNION ALL SELECT 'payrec', COUNT(*), GROUP_CONCAT(id ORDER BY id) FROM payrec
UNION ALL SELECT 'patient_emr', COUNT(*), GROUP_CONCAT(id ORDER BY id) FROM patient_emr
UNION ALL SELECT 'user', COUNT(*), GROUP_CONCAT(id ORDER BY id) FROM user
UNION ALL SELECT 'patient', COUNT(*), GROUP_CONCAT(id ORDER BY id) FROM patient
UNION ALL SELECT 'procrec', COUNT(*), GROUP_CONCAT(id ORDER BY id) FROM procrec
UNION ALL SELECT 'vitals', COUNT(*), GROUP_CONCAT(id ORDER BY id) FROM vitals
UNION ALL SELECT 'modules', COUNT(*), CONCAT(COUNT(DISTINCT module_class), ' distinct module_class') FROM modules
UNION ALL SELECT 'log', COUNT(*), NULL FROM log
UNION ALL SELECT 'multum', COUNT(*), NULL FROM multum
UNION ALL SELECT 'userpreferences', COUNT(*), NULL FROM userpreferences
UNION ALL SELECT 'i18nlanguages', COUNT(*), NULL FROM i18nlanguages;
```

Recorded output (`mysql -h127.0.0.1 -P33306 -ufreemed -pfreemed -B freemed -e "<query>"`):

```

entemplate      1       1
payrec          1       3
patient_emr     1       5
user            2       1,2
patient         0       NULL
procrec         0       NULL

log             748     NULL      <-- NOT pinnable, see below: it grows with every request
multum          15785   NULL
```

### Which of those the recorded outcomes actually depend on

| table | rows / ids | what it decides |
|---|---|---|
| `payrec` | 1 row, id 3 | `PaymentModule` → `SKIP: GetList() returned 1 rows, none with an id`. **This is the entry the 2.6e cascade incident moved** (1 → 0 rows) and the only one of the two artifacts' 136 entries that ever differed. |
| `entemplate` | 1 row, id 1 | `EncounterNotesTemplate` and `EncounterNotesTemplate#2` → both `OK`. |
| `modules` | 135 rows, 134 distinct `module_class` | The entry count: 135 registry rows + the negative control = 136 entries. It also carries the two hand-written rows below (one of which is the duplicate class). |
| `log` | non-empty (748 at recording time) | `LogModule` → `OK`. Only non-emptiness is required; the exact count is deliberately *not* part of the fingerprint (the application writes an audit row per request — including for the verify probes themselves, which took it to 771 during the fix round). |
| `multum` | 15785 rows | `MultumDrugLexicon` → `OK`. |
| `userpreferences` | 1 row | `UserPreferences` → `OK`. |
| `i18nlanguages` | 5 rows | `i18nLanguages` → `OK`. |
| `patient`, `procrec`, `vitals` | 0 rows each | Must stay empty. These are the tables the sweep's `SKIP`-on-empty-table limit is about, and `vitals` is the table the 2.6e live probes seeded (and cleaned up) on top of this state. |
| `patient_emr` | 1 row, id 5 | No registered module lists `patient_emr` (only `Annotations` reads it by explicit id), so this does **not** move an entry — it is recorded because it is part of the seed and because its id 5 is the visible trace of the incident in `sweep-notes.md` section 7. |
| `user` | 2 rows, ids 1,2 | Pre-existing deployment seed, not written by `seed-verify.sql`. The smoke needs *a* patient id (it falls back to 1 when `patient` is empty), not a user id. |

The 6 `OK` entries are therefore fully accounted for:
`EncounterNotesTemplate`, `EncounterNotesTemplate#2` (entemplate), `LogModule`
(log), `MultumDrugLexicon` (multum), `UserPreferences` (userpreferences),
`i18nLanguages` (i18nlanguages).

### The two `modules` rows that are NOT generated by `--register`

`modules` has no AUTO_INCREMENT column; its explicit primary key is `module_uid`.
The other 133 rows are generated by `php tests/security/module_smoke.php --register`
with `module_uid = md5(module_class)` formatted as a UUID (deterministic) and
`module_stamp = filemtime(module file)` (NOT deterministic — and no smoke outcome
reads it). These two are hand-written by `seed-verify.sql`:

```
module_uid                            module_class           module_table  module_path                                                     module_version  module_category  module_associations  module_stamp  module_hidden
11111111-1111-1111-1111-111111111111  DemoPayments           demo          /tmp                                                            1.0             test             billing              0             0
709a8d12-3799-46a7-8648-567b904349f2  EncounterNotesTemplate  entemplate    lib/org/freemedsoftware/module/EncounterNotesTemplate.class.php  0.1             encounter        encounter            0             0
```

The `DemoPayments` row is a deliberate `module_path='/tmp'` (the smoke's
`EXC: registry row does not resolve to a file` control); the `709a8d12-…` row is
the duplicate `EncounterNotesTemplate` class that produces the `#2` key.

### AUTO_INCREMENT counters and other deliberately unpinned values (informational only — NOT part of the contract)

Observed at fingerprint time: `patient` 2, `procrec` 2, `vitals` 2, `entemplate` 2,
`patient_emr` 9, `payrec` 6.

These are **not** reconstructible and nothing may depend on them: the
`patient_emr` companion row is written by the `payrec_Insert` trigger (so its id
is whatever the counter was at the time), and later probe runs consumed further
ids — `patient_emr` was observed at 10 by the end of the fix round. They are
recorded only so that a reader who sees a number move knows it is expected. This
is exactly why `seed-verify.sql` pins the companion row with an `UPDATE … SET id =
5` and not with `ALTER TABLE … AUTO_INCREMENT`.

Two more values are deliberately excluded from the fingerprint:

* **`log.*`** — the application's audit log, written per request (748 → 771 during
  the fix round). Only non-emptiness matters; the fingerprint row for `log` is a
  check that the table is not empty, not a count to match.
* **`patient_emr.stamp`** — `NOW()` when the trigger wrote the row, and refreshed
  to `NOW()` again by the `payrec_Update` trigger whenever `seed-verify.sql` is
  re-applied. Nothing compares it.

## The check procedure

```sh
# 1. from a fresh reduced seed: register every module class, then apply the seed
docker exec -T freemed-verify-apache php tests/security/module_smoke.php --register   # once
docker exec -i freemed-verify-db mysql -ufreemed -pfreemed freemed < tests/security/evidence/seed-verify.sql

# 2. fingerprint it and compare to the block above
docker exec -i freemed-verify-db mysql -ufreemed -pfreemed -B freemed -e "$(sed -n '/^SELECT .entemplate/,/^UNION ALL SELECT .i18nlanguages/p' tests/security/evidence/seed-fingerprint.md)"

# 3. only then compare the artifacts
cmp tests/security/evidence/module-smoke-before.json tests/security/evidence/module-smoke-after.json
```

`seed-verify.sql` prints the same assertion rows at its end, so step 1+2 collapse
into one command if the file is applied with `-t` / interactively.

### What a mismatch means

A differing count is **seed drift**, not a sweep regression:

* `payrec` 0 rows → something deleted the payrec row again (a `DELETE FROM patient`
  cascades through `payrec_ibfk_1` and `patient_emr_ibfk_1`; a `DELETE FROM procrec`
  cascades through `payrec_ibfk_2`). See `sweep-notes.md` section 7.
* `payrec` 2 rows → a seeded `procrec` row fired `procrec_Insert`, which inserts a
  `payrec` row of its own.
* `modules` ≠ 135 → `--register` was not run, or one of the two hand-written rows
  is missing (`134` if `DemoPayments` is gone, `134`/`135`-entry consequences in
  `sweep-notes.md` section 9).

Fix the seed and re-run; do **not** edit `module-smoke-before.json` or
`module-smoke-after.json` to absorb the difference, and do not delete a row that
the recorded state requires.
